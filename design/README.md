# Tazrout — Design Resources

Welcome to the **design/** directory of the Tazrout project.  
This folder is the central source of truth for all UI/UX assets, specifications, and documentation used to build the **Flutter desktop dashboard** for the Tazrout Agricultural IoT Monitoring System.

Whether you are a frontend developer, a designer reviewing consistency, or a stakeholder exploring the project, this directory gives you a complete view of how the dashboard looks, behaves, and connects to the backend.

---

## Folder Structure & Contents

```
design/

├── components/           # Isolated reusable UI widgets (as exports)

│   ├── DESIGN_SYSTEM.md
│   ├── SCREEN_SPECIFICATIONS.md

```

---

### `assets/` – Raw Graphical Files

Contains all the visual building blocks that are not generated by code:

- **Icons** – Custom SVG icons used across the sidebar, status badges, and control buttons (e.g., reboot, power, clock, humidity).
- **Amazigh Motifs** – Authentic local geometric patterns (diamonds, cross‑stitches, chevrons) used as subtle background textures on cards and decorative borders. These give the dashboard its unique Algerian identity.
- **Logos** – The Tazrout wordmark and plant symbol in various resolutions.

---

### `components/` – Reusable UI Widget Exports

This folder holds pre‑exported graphics of isolated UI elements that are used repeatedly across screens.  
Examples include:

- **Emergency Stop button** – The oversized, stitched visual that prevents accidental clicks.
- **Status badges** – Color‑coded pills (ONLINE = green, OFFLINE = red, ALERT = amber, CRITICAL = red).
- **Sparkline charts** – Minimal area/line charts used on the Home screen’s Performance Monitor.
- **Clock & calendar widgets** – The analogue clock face and the calendar widget with Amazigh pattern borders.
- **Zone card variants** – Expanded vs. collapsed states, online/offline treatments.

These assets help ensure consistency when rebuilding components in Flutter.

---

### `docs/` – Core Design & Technical Documentation

This is the **most important folder** for developers implementing the frontend. All files are written to be the single source of truth for design decisions and technical requirements.

| File | Description |
|------|-------------|
| **COMPONENT_CATALOGUE.pdf** | A comprehensive visual reference showing every UI element, its states (default, hover, active, disabled), and how data is displayed in tables and cards. It includes system controls, sensor metrics, AI decision cards, and zone variations. |
| **DESIGN_SYSTEM.md** | Defines the foundational “DNA” of the app: colour tokens (agricultural green, semantic status colours), typography (Inter for UI, Poppins for headings), spacing scales, border radii, and component state colours. Use this to configure your Flutter theme. |
| **SCREEN_SPECIFICATIONS.md** | A technical breakdown of every screen. It describes the layout, UI components, interactive states, and **exactly which backend APIs and WebSocket events** each widget must consume. This is your guide to wiring the frontend to the backend. |
| **DESIGN_DECISIONS.md** | A log explaining the “why” behind major UI/UX choices. Topics include: why light mode is default, why colour is never the sole differentiator (accessibility), the rationale for the persistent sidebar, and why we use an analogue clock. |

---

### `mockups/` – Structural Skeletons (Wireframes)

This folder contains the **structural skeletons** of the screens — not the final polished visuals, but the layout architecture that defines how containers, grids, and components are nested.  
Use these to understand the **“bones”** of the Flutter layout before styling is applied. They are especially useful when you need to re‑create the responsive grid system (e.g., the 3‑column zone grid, the two‑column analytics layout).

---

### `screens/` – Final High‑Fidelity Exports

Fully styled screens, organised by theme:

- **`Light-Theme/`** – The default interface, optimised for data readability in well‑lit daytime environments.
- **`Dark-Theme/`** – A specialised theme for low‑ambient‑light control rooms or night‑shift monitoring.

Screens included:  
Home, Zones, Analytics, Emergency Control, Settings, Help Center, User Manual, and the QR/Contact Card overlay.  
These exports match the final approved designs and should be used as the visual target during implementation.

---

### `FIGMA_LINKS.md` – Master Figma Files

Contains direct links to the live Figma workspaces:

- **Design System & Mockups** – For inspecting exact spacing, typography, and colour values.
- **Components & Screens** – For viewing interactive prototypes and component variants.
- **Amazigh Patterns** – For accessing the original decorative pattern layers.

Use these links when you need to extract precise CSS/Flutter values (e.g., padding, drop‑shadows) or export assets in a different format.

## How to Use This Folder

If you are **implementing the frontend** (Flutter desktop), follow this workflow:

1. **Start with the design system** – Read `DESIGN_SYSTEM.md` to set up your global theme, colours, and text styles.
2. **Understand the screen requirements** – Open `SCREEN_SPECIFICATIONS.md` to see the exact layout, components, and API bindings for the screen you are building.
3. **Refer to visual references** – Use `screens/` and `COMPONENT_CATALOGUE.pdf` to see how the final UI should look in both light and dark modes.
4. **Understand the “why”** – If a design choice seems unusual, check `DESIGN_DECISIONS.md` for the accessibility or functional reasoning.
5. **Extract exact values** – Use `FIGMA_LINKS.md` to inspect spacing, colour hexes, or export missing assets directly from Figma.

If you are a **designer or reviewer**, this folder gives you:
- A complete inventory of all UI assets and their intended behaviour.
- A transparent record of the design rationale.
- The technical requirements that tie design to implementation.
